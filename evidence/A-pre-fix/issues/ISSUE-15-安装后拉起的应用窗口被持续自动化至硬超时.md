# ISSUE-15｜安装完成后被拉起的应用窗口被误当作"安装向导"，持续自动化到硬超时（高）

- **严重级别**：高（每个"装完自动启动"的软件都会白吃一整个 timeout，还可能在用户应用里乱点）
- **状态**：待修复
- **关联验收项**：F9 / A30 / F14
- **发现环境**：已提权，真实软件样本 `01-Inno Setup`

## 一、问题现象

`ShareX-17.0.0-setup.exe` **安装其实是成功的**（拿到 `S1|ShareX 17.0.0` + `S2|新增 48 个文件`），
但安装完成后 ShareX **自动启动了主程序**，工具于是把这个**应用主窗口**当成了安装向导，一直尝试自动点击，
直到 **305.3 秒硬超时**才被终止。

```text
final_status = install_completed   conf = high
notes        = "terminated on timeout; installation evidence still collected"
attempt[1]: silent_install  exit=null  result=killed_on_timeout  dur=305.3s
            term=terminated  err=deadline_or_interrupt
            evidence = ["S1|ShareX 17.0.0","S2|新增 48 个文件或目录实体"]
            gui      = ["确定@win32"]
```

## 二、证据

### 2.1 日志显示工具在**应用窗口**里找安装按钮（`elevated-real\01-group.log`）

```text
[调试] 【界面】界面识别详情：窗口 "ShareX 17.0"（PID 1652）未识别到可点击控件：
       行 0, 未排序。/edit/可用=true/选中=false、Hotkey 行 0/edit/可用=true/选中=false、
       Description 行 0/edit/可用=true/选中=false、 ……、截图/button/可用=true/选中=false
[信息] 【执行】执行等待中：已用时 302 秒，无进展 1 秒，最近信号=gui_change，监控PID=[1652]
[信息] 【执行】本轮尝试结束：超时被强制终止，耗时 305.3 秒
```

窗口标题是 `ShareX 17.0`（**应用主窗口**），控件是 `Hotkey / Description / 截图`（**ShareX 自己的功能**），
与"安装向导"毫无关系。

### 2.2 为什么吃不掉 idle 超时、只能等硬超时

```text
已用时 302 秒，无进展 1 秒，最近信号=gui_change
```

ShareX 的窗口一直在重绘（GUI 活动信号持续变化），于是 `idle_timeout_sec=60` **永远触发不了**，
只能等 `--timeout` 的硬上限。本例用了 300 s；若按默认 600 s 跑，就是 600 s。

## 三、期望行为

1. **安装证据已足够时立即收工**：一旦拿到 S 级证据（本例 `S1+S2`）且**安装器主进程已退出**，
   就不应再为"仍然存活的应用进程"继续等待；剩余窗口/进程应记为"安装后启动的应用"，**移出 GUI 自动化目标**。
2. **GUI 自动化的目标进程集合要收敛**：只应操作**安装器自身进程树**里的窗口。
   当前窗口筛选显然过宽（把安装器启动的子应用也算进来了）。建议：
   - 用安装器进程 PID 及其**安装期间**创建的子进程做白名单；
   - 或对"安装成功后新启动的进程"直接打标记并排除。
3. **加一层"这不是安装向导"的守卫**：窗口标题/控件与安装动作关键词完全不匹配时不应无限轮询；
   可统计"连续 N 次未识别到可点击控件即放弃该窗口"。

## 四、影响面

**"安装完成后自动启动程序"是 Windows 安装器的常见行为**（ShareX、Notepad++、QQ、各类工具都这样）。
如果每个这样的样本都要吃掉 300–600 s，批量跑 `300` 个样本的耗时会被拖垮；
而且在用户真实应用窗口里乱点存在**误操作风险**（本例已经点了一个 `确定`）。
