## 二、统计口径（必读）

### 2.1 为什么没有单一成功率

本套件的测试**跨 3 个工具构建、2 种权限上下文、多个批次**：

| 构建 | 大小 | 时间 | 对应证据 |
|---|---|---|---|
| #1 修复前 | 10,038,272 B | 2026-10-11 | evidence/A-pre-fix |
| #2 修复后 | 10,235,904 B | 2026-10-12 | evidence/B-post-fix |
| #3 当前分发版 | 10,926,592 B | 2026-10-13 | 仅做过冒烟验证（evidence/smoke-2026-10-14） |
| #4 当前分发版 | 7,758,848 B | 2026-10-14 | evidence/sample-run-2026-10-14（120 自制备样 + 4 第三方抽测） |

> ⚠️ 按行业惯例与用户要求：**不同版本/环境的报告不得直接混合统计**。
> 表中每一段只对应一个构建 + 一种权限。构建 #3 **没有**全套件结果；
> 构建 #4 覆盖了**全部 120 个自制备样**，但第三方组 01–06 只抽测了 4 个。

### 2.2 分母怎么算

```text
分母 = 该段覆盖的输入样本数 − skipped
安装成功率 = install_completed / 分母 × 100%
```

- `skipped` **排除出分母**：它表示"未执行"（空文件、无宿主、命中黑名单），不构成安装能力证据。
- `install_unverified` / `install_partial` / `triggered` / `killed_on_timeout` / `failed`
  **在分母内但不计入分子**——它们是"没装成功"或"没验证成功"。
- `already_installed` 单列，不并入成功率。

### 2.3 容器展开实体必须排除

一次"目录/压缩包"输入会展开出大量子项。本套件实测：

| 项 | 数量 |
|---|---|
| 结果 JSON 中的行总数 | 3693 |
| 其中**输入样本**（路径位于 samples\ 下） | **290** |
| 其中**容器展开实体**（位于 %TEMP% 等） | **3403（已排除）** |

代表例：`MobaXterm_Installer.zip` 单独解出 1300+ 个文件；`putty-0.85-w64.zip` 解出数百个。
若不做路径过滤，`skipped` 会被灌到 2500+，统计完全失真。

**判定方法**：只用 `file_path` 的**完整路径**前缀判断，**不能只比文件名**——
解压产物里也有 `setup.exe`、`app.exe` 这类与样本同名的文件。

### 2.4 样本去重

同一批结果里，同一样本可能因重跑出现多次。本报告的处理：**按段内"每个输入样本取最后一次结果"去重**。
因此 `per-sample.csv` 的行数（247）等于各段去重后样本数之和，而非原始结果行数（290）。

## 三、状态字段来源

所有状态取自 AutoTrigger 结果 JSON 的 `results[].final_status`；
证据 ID 取自 `results[].attempts[].install_evidence[].id`；置信度取自 `install_confidence`。
**没有手工改写任何状态。**
