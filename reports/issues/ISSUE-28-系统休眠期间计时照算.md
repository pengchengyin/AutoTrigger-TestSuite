# ISSUE-28｜系统休眠/挂起期间计时照算，单文件耗时出现 7 小时（低）

- **严重级别**：低（不影响判定结果，但会让日志/耗时统计严重失真，并可能误触超时）
- **状态**：待修复（或至少在文档中声明）
- **关联验收项**：A30（全部与"时长"有关）
- **发现环境**：测试机在跑批过程中进入睡眠

## 一、问题现象

跑 `A30-02` 时，机器在 **12:44:12 进入睡眠**（系统日志可证），
约 **19:56** 唤醒后，工具把整段睡眠时间计入了单文件耗时：

```text
[信息] 【执行】本轮尝试结束：超时被强制终止，耗时 26118.4 秒
[信息] 【结果】本次运行结束：总耗时 26158.5 秒，退出码 0
结果 JSON：dur = 26118.3881395 秒   （≈ 7 小时 16 分）
```

日志时间戳的"断档"很直观：

```text
2026-10-11 12:43:59 [信息] 【执行】执行等待中：已用时 151 秒，……
（空白 7 小时）
2026-10-11 19:56:46 [信息] 【执行】本轮尝试结束：超时被强制终止，耗时 26118.4 秒
```

## 二、系统侧证据

```text
Kernel-Power 事件 ID 42（进入睡眠）   TimeCreated = 2026/10/11 12:44:12
当前时间 2026-10-11 19:58:28，上次启动 09:53:47
```

## 三、影响

1. **耗时统计失真**：`attempts[].duration_sec` / 总耗时会出现 7 小时这种数字，
   按"时长"做断言或监控（A30 整组、批量吞吐统计）都会误判；
2. **可能误触超时**：唤醒瞬间"已用时"暴涨，工具会立即判定超时并强杀**本来还在正常安装**的进程；
   对慢安装器（如 `INNO-05` / `A30-01`）在笔记本合盖场景下很现实；
3. **排查困难**：日志里出现 7 小时空档，使用者很难第一时间想到是机器睡了。

## 四、期望行为

1. **区分"运行时长"与"墙钟时长"**：优先用可感知挂起的计时（或减去挂起区间），
   至少把"检测到明显时间跳变"记成一条 warning；
2. **唤醒后重新评估**而不是直接判定超时：先看进程树是否仍在活动，再决定是否终止；
3. **文档化**：在 README/PRD 里说明"休眠期间的计时口径"，否则 A30 之类的时长验收在笔记本上无法稳定复现。
